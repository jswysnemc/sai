# Lua 插件体系

## 目标

在 `feat/lua-plugin-ecosystem` 分支将 Sai 中耦合过深的可选业务迁移到 Lua 插件，建立可安装、配置、验证和组合的扩展体系。分支创建和运行时骨架不代表目标完成；必须有实际业务迁出，并通过真实入口验证。

Rust 宿主负责会话事实、权限、资源约束、取消和平台能力。Lua 插件负责可选业务、工具定义、命令和生命周期扩展。插件不得读取整份 AppConfig，也不得绕过现有工具授权入口。

## 参考依据

- [DeepSeek Harness 架构](https://github.com/deepseek-ai/deepseek-harness/blob/47f943859bef60e4160492346772ded9b24f765a/docs/architecture.md)：能力接口、实现和消费者分开；注册属于插件生命周期，卸载后撤销；模型可见内容必须进入会话记录。核对了本地同一提交的源码与文档。
- [pi 扩展文档](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/extensions.md)：统一注册工具、命令和事件；支持加载、重载以及会话上下文。原 pi-mono 项目的文档当前由此仓库提供。
- [mlua](https://docs.rs/mlua/0.12.1/mlua/)：使用 Lua 5.4、vendored、async、send 和 serde。以已下载的 0.12.1 源码签名为准，不直接采用文档检索中的生成示例。

## 模块职责

| 位置 | 职责 |
| --- | --- |
| `crates/sai-plugin-runtime` | 不依赖 Sai 应用配置的清单、源码快照、Lua 执行和宿主契约 |
| `src/plugins` | 配置与发现、宿主能力实现、注册适配、安装管理 |
| `src/plugins/session.rs` | Agent 内插件实例共享、跨 Agent 隔离、重载复用判定 |
| `src/plugins/events.rs` | Agent 与逻辑模型请求的生命周期范围 |
| `src/plugins/services` | 绑定当前模型、工具目录和调用链，执行单次模型与工具请求 |
| `src/tools/registry_plugin_services.rs` | 将实时工具权限、插件授权与当前模型交给调用服务 |
| `src/plugins/compatibility` | 旧业务设置的定向兼容；派生凭据仅保留在运行时快照 |
| `src/plugins/http.rs` | 通用 HTTP 执行、逐次重定向授权、凭据处理和响应限制 |
| `plugins/<id>` | 随二进制发布的 Lua 业务包；业务源码不再置于 `src/tools` |
| `src/cli/plugins.rs` | 面向插件开发者和使用者的管理入口 |
| `src/cli/repl/plugin_commands.rs` | TUI 会话内命令、重载、进度和取消 |
| `src/tools` | 统一的工具注册、权限和结果交付；不按外部插件逐项编写分支 |

工具定义、执行和插件适配分别位于 `tool_spec.rs`、`registry_execution.rs`、`registry_plugins.rs`。`registry.rs` 保留注册表组合和原有公开导出。子任务的模型请求与进度管理也已从主运行器拆出，生命周期接入不再扩大原单文件。

## 已落地的版本 1

独立运行时使用 Lua 5.4，包含包验证、受限模块加载、工具、命令、事件和 HTTP、模型、工具调用、JSON、文本、时间能力。`online-man`、`deepseek-status`、`archlinux`、`fcitx-wiki`、`protondb`、`web-search`、`linux-game-signals` 与 `linux-game-investigation` 已迁为随程序嵌入的八个 Lua 包，共提供 13 个工具；相应 Rust 业务实现已删除，公开工具名称保持兼容。

CLI 提供创建、验证、安装、替换、配置、授权、启停、移除和命令执行。TUI 提供 `/plugins`、`/plugins reload` 与 `/plugin <id>/<command>`。模型工具通过原有共用注册入口进入 CLI、TUI、Web 和子任务，直接用户命令目前只有 CLI 与 TUI 入口。

原生文件与进程接口、持久插件存储、主 Agent 模型上下文变换、插件界面组件和远端包分发尚未开放。插件已能在授权范围内调用现有文件和进程工具。后续业务迁移见[迁移清单](migration.md)。

## 契约原则

1. 每个插件有独立 `sai-plugin.json`，包含 API 版本、稳定 ID、版本、入口、能力声明和资源限制。
2. 从受信任的用户插件目录或显式安装路径加载。工作区中的文件不能仅因存在便获得自动执行权限。
3. 清单和源码读取形成固定快照。新会话或显式重载使用新快照，已开始的调用保持原版本。
4. Lua 无原生文件、进程、动态库或任意网络入口。宿主能力必须满足声明与用户授权的交集。
5. 外部工具使用包含插件 ID 的名称，不能覆盖核心工具。迁移的内置工具保留现有公开名称，避免破坏 Agent 白名单与会话记录。
6. 工具参数采用 JSON Schema。插件声明的写入能力仍走 Sai 已有权限检查；只读 POST 查询额外要求精确端点声明及用户授权，不扩大到其他路径或其他写入方法。
7. 配置、Lua 堆、指令数量、执行时长、请求响应和结果大小均有明确边界。加载失败不能留下部分注册。
8. 事件接口区分可阻止执行的检查与只观察结果的通知。插件只能收窄权限，不能替代宿主批准。
9. 命令、工具和监听器由同一插件实例持有；禁用和重载不遗留旧注册。
10. Web、TUI、CLI 和子任务通过同一注册适配使用插件，避免分别维护功能名单。

## 实例与执行边界

`ToolSpec` 的插件后端只保存插件 ID 和包内工具或命令名，`ToolRegistry` 持有 `PluginSession`。同一 Agent 的克隆和过滤工具表共享实例；构造新 Agent、切换会话或创建子任务时重建 Lua 状态。插件会话标识与网格权限归属标识分开，工作目录也由宿主提供，模型参数不能覆盖。

模式切换、工具表替换和显式重载通过包源码、设置、授权的摘要识别未变更实例。更新后的工具表复用未变更插件；已禁用或发生变化的插件不再继承旧实例。TUI 重载重新构建子任务工具闭包，并防止早先启动的 MCP 预热结果覆盖新快照。已经执行中的调用持有自己的旧快照，直至完成或取消。

Lua 状态属于 Agent 实例内存，不是持久化会话存储。不同入口对 Agent 的复用时长不同，插件不能依赖全局变量在进程重启或会话切换后保留。

`agent_start/end` 包围一次用户请求或子任务段，`turn_start/end` 与 `message_start/end` 包围一次逻辑模型请求，传输重试位于同一范围内。工具检查统一放在宿主授权之后、真实调用之前，只接受继续或拒绝；观察回调失败独立诊断。外部取消回收 Future，不另起后台任务补发结束回调，避免产生新的自动续聊工作。

插件计算在阻塞线程中执行，指令 Hook、堆上限与超时约束 Lua；受管 HTTP 在取消时停止。此边界不等于操作系统进程隔离，Lua 堆限制也不代表整个进程的内存上限。

### 模型与工具的调用服务

`InvocationServices` 只提供模型单次完成、已授权工具目录和显式工具执行，运行时不包含 Sai 配置或业务循环。每次需要这些能力的调用绑定一个新服务；`InvocationLease` 在成功、错误和取消时撤销权限并释放服务引用，事件回调不绑定服务。模型与工具次数预算也以本次回调为范围。

服务复制父 Agent 的完整工具表并 fork 插件 VM，再用单独的名称集合限制调用方。这样 A 可以调用 B，B 继续使用自己的 C 依赖，而 A 不会获得 C 权限；B 的依赖仍必须存在于原 Agent 白名单。嵌套调用沿用实时权限配置、工作目录和网格归属，独立的插件会话标识不扩大跨会话权限。

Tokio 调用链记录祖先插件 ID 和进程内 VM 标识，不持有祖先 VM。工具入口先拒绝递归及超过八层的调用，再分发事件；原生包装器持有旧注册表时，只 fork 其中正在执行的监听器实例。工具检查仍完整执行，避免把跳过监听器当作死锁修复。

Agent 新建、重载、模式切换、工具表替换和 SubagentRunner 都绑定实际选定的客户端。CLI 配置来源延迟到首次模型请求才初始化；模型地址与凭据留在 Rust。Lua 只维护自己的文本消息、选择工具并决定继续或收尾。请求必须以 user 消息结束；宿主不会自动执行模型建议，内部执行别名也不会提升成已授权名称。

模型流接收时累计正文、思考和工具参数字节，超限即停止，不等连接结束。请求、工具目录及最终序列化结果继续执行大小检查。模型请求超时可由 Lua 捕获，外部取消会停止当前宿主 Future，不生成额外后台任务。

## 配置与兼容迁移

插件配置独立保存为 Sai 配置目录中的 `plugins.jsonc`，避免扩大已有主配置类型。现有可选工具开关只作为相应内置插件的迁移默认值；显式插件配置优先。已迁移业务原有设置通过独立兼容模块定向传递，新插件只声明自身配置，不增加 AppConfig 字段。

旧功能必须通过 Lua 实现执行，不能仅用 Lua 包装原有 Rust 业务函数。HTTP、文本解码、时间和 HTML 转文本或 Markdown 等通用能力保留为宿主能力。HTML 转换统一放在运行时的 `text.rs`，业务包负责页面范围、截断规则和返回格式。

Arch 包内部按软件包、状态和 Wiki 查询拆分；Fcitx 的主题、双语规则、正文提取和响应格式各自独立；ProtonDB 的搜索、评论地址计算和评论格式分别维护。新增内置包由资源目录自动发现，Rust 层只保留必要的旧配置兼容。

网页搜索的选择顺序、请求构造、失败回退和结果格式化全部位于 `plugins/web-search`。六个供应商各有独立 Lua 文件，共用包内配置及结果格式。`src/tools/web_fetch.rs` 负责通用网页读取；原有 Rust 搜索注册及供应商模块已删除。

搜索兼容层以旧 `WebSearchConfig` 为默认值，再按字段合并显式插件设置。原始设置与派生设置分开保存，管理命令只写原始设置；凭据解析结果参与实例修订比较，使重载能识别环境值轮换。自定义地址只转换成来源和 POST 查询路径，不将查询参数写入清单展示。显式授权保持固定，新地址仍须在其范围内。

只读 POST 使用通用 `http_read_only_post` 能力；查询语义由插件契约保证，宿主执行精确路径及方法检查，并在每次重定向后重新检查。HTTP 请求绑定独立放在运行时的 `http.rs`，请求和回调时长分别受清单限制，普通插件默认仍为 30 秒和 20 秒。

`linux-game-signals` 负责 Steam、ProtonDB、Can I Play on Linux 和 AreWeAntiCheatYet 四来源采集，以及名称归一化、摘要、判定和置信度。`linux-game-investigation` 负责提示词、完整模型循环、逐项工具执行、预算收尾、进度、统计和报告整理；它通过共用工具表调用采集包，原 Rust 游戏调查模块和专用提示词已删除。采集工具可以独立调用，禁用采集包后调查入口在初始化模型之前报错。

旧游戏配置只向调查包传递工具步数、进度模式和语言，不传供应商配置。两个包独立读取旧开关作为缺省值，显式插件配置分别优先。调查为无工具收尾保留模型及消息额度，统计每次响应只累计一次，修正原实现重复计入末次用量的问题。

游戏证据沿用原有字段，`verdict.traffic_light` 改用 `red`、`yellow`、`green`，避免把图形字符作为界面状态。来源缺失、空正文、JSON null、状态优先级及 Unicode 截断均有原版对照。网络错误文本由统一宿主生成，保留失败尝试而不承诺沿用旧 HTTP 库的错误措辞。

## 验证与完成依据

- 运行时契约测试覆盖清单、加载事务、命名冲突、模块路径、权限、资源限制、取消和事件生命周期。
- 内置迁移测试使用可复现 HTTP 数据，验证实际 Lua 包输出，而非测试一份平行的 Rust 实现。
- 从 Sai 工具注册表和命令行验证加载、调用、禁用、恢复和配置覆盖。
- 既有 Rust 与 Web 测试保持通过，Windows、Linux、macOS 构建验证 vendored Lua 的可移植性。
- 迁移清单逐项记录实际证据，未实现能力保持待办，不能用局部测试证明整个目标完成。
